고객·과제 정의 (고객 제공 원문 요약)

# 과제 담당 현재 방식 어려움 검토 방향 소요 시간
1 Google Play / App Store 리뷰 대응 자동화 운영 담당자가 리뷰를 직접 확인·번역·답변(미리 쓴 답변 사용) 다른 일정 때문에 며칠 치를 한 번에 처리 수집 → 유형 분류 → 번역 → 답변 초안 → 담당자 검수 → 답변 등록 리뷰 1개당 2분
2 게임 내 주간 이벤트 제작 자동화 운영·디자인 매주 주제 선정·문구·번역·이미지·스토어 등록을 각각 진행 반복 과정, 국가별 문구·이미지 제작 시간 주제 선정 → 제목·내용 → 이미지 → 다국어 번역 → 스토어 이벤트 등록 운영 주 1~2시간 / 디자인 1~2일
3 Meta / Google 광고 운영 및 성과 분석 자동화 마케팅 담당자가 광고 데이터를 직접 확인·분석·운영 국가·캠페인·소재별 반복 분석 데이터 수집 → 성과 분석 → 문제점 파악 → 예산·다음 액션 제안 → 리포트 매일 1시간 이상
  • 대표작: 「원시인 형님들 키우기 : 문명 x 방치형 RPG」 — Play com.primitivebrother.thunder.google, App Store 1490207503
  • 사용자 요구: 과제 1은 실제 리뷰로 웹서비스를 만들어 https://namojo.github.io/game-review/ 에 배포, 과제 2는 codex-image 로 이벤트 이미지 제작, 과제 3은 IT마케팅 전문가 관점의 구현 방안. 최종 산출물은 HTML 보고서 + Markdown(로컬 deliverables/). 공개 사이트에는 리뷰 서비스만 올린다.

작업 절차

0단계: 기존 작업 확인

  1. _workspace/ 가 없으면 → 처음부터.
  2. 있고 부분 요청이면 → 해당 단계만: - "리뷰 데이터 갱신" → 1단계 수집(새 기간) → 새 id 만 배치 → 2A → 3 병합 → engineer 에게 커밋·푸시 지시 - "다음 주 이벤트" → planner 에게 캘린더의 다음 주제로 새 {event_id} 지시 → designer → qa(C) - "과제 3 보완" → strategist 에게 해당 절 수정 → qa(D) - "보고서 수정" → editor → qa(E)
  3. 있고 새 입력(다른 게임·다른 고객)이면 → _workspace/ 를 _workspace_{YYYYMMDD_HHMM}/ 로 옮기고 처음부터.
  4. 진행 상황은 _workspace/progress.md 에 단계별로 적는다(TaskCreate 를 쓸 수 있으면 함께 쓴다). 사용자에게 단계가 끝날 때마다 한국어로 짧게 보고한다.

python3 -m venv --system-site-packages .venv && ./.venv/bin/pip install -q google-play-scraper   # 최초 1회

2단계: 병렬 실행 (한 메시지에서 동시에)

  • 2A 리뷰 분석: manifest.json 의 배치마다 Agent(subagent_type: "review-ops-analyst", description: "리뷰 배치 {name} 분석", prompt: "배치 _workspace/02_batches/batch_{name}.json 을 처리해 _workspace/03_analyst_drafts_{name}.json 으로 저장하고 validate_drafts.py 로 오류 0을 확인한 뒤 보고하라.") — name 없이 백그라운드.
  • 하네스를 만든 같은 세션에서는 새 에이전트 유형이 아직 등록되지 않아 이름 없는 호출이 Agent type not found 로 실패한다(2026-10-07 관찰). 이때는 name: "analyst-{batch}" 를 붙여 호출하거나 general-purpose + model: "sonnet" 으로 호출하고, 어느 쪽이든 프롬프트 첫 줄에 "역할 정의 .claude/agents/review-ops-analyst.md 를 먼저 읽고 따르라"를 넣는다. 지속형 에이전트(engineer 등)의 프롬프트에도 같은 문장을 넣는다.
  • 2B engineer: Agent(name: "engineer", subagent_type: "review-service-engineer", prompt: 과제 1 정의 + "data/reviews.json 은 3단계에서 전달한다. 그 전에는 raw 파일로 임시 데이터를 만들어 화면을 개발하라. 배포는 지시 전까지 하지 마라.")
  • 2C planner: Agent(name: "planner", subagent_type: "liveops-event-planner", prompt: 과제 2 정의 + 오늘 날짜 + "이번 주 제작 대상 1건 키트와 8주 캘린더, 키아트 브리프를 만들어라.")
  • 2D strategist: Agent(name: "strategist", subagent_type: "ads-growth-strategist", prompt: 과제 3 정의 + "IT마케팅 전문가 관점에서 guide.md 와 동작하는 sample/ 을 만들어라.")

3단계: 연결 (완료 알림을 받는 대로)

  • 2A 전부 완료 → validate_drafts.py --all _workspace (오류가 있는 배치만 같은 유형으로 다시 맡긴다, 1회) → merge_for_site.py --workspace _workspace --out game-review/data/reviews.json → SendMessage({to: "engineer"}, "최종 데이터 준비 완료: game-review/data/reviews.json. 실제 데이터로 화면을 확인하고 보고하라.")
  • planner 가 브리프·copy.json 완료를 보고 → Agent(name: "designer", subagent_type: "event-visual-designer", prompt: 브리프 경로 + copy.json 경로 + event_id)
  • designer 가 문구 길이 문제를 보고 → planner 에게 전달 → 수정 후 designer 에게 합성만 다시 지시.

4단계: QA 루프

  • 첫 생산자가 완료를 보고하면 Agent(name: "qa", subagent_type: "consulting-qa", prompt: "트랙 {A|B|C|D} 를 검사하라. 대상 경로: …"). 이후 트랙은 SendMessage({to: "qa"}, "트랙 X 검사").
  • qa 의 실패 항목 → 해당 생산자에게 SendMessage 로 그대로 전달 → 수정 보고 → qa 재검증. 트랙당 최대 2회 왕복. 그래도 실패하면 남은 이슈를 보고서의 "알려진 제한"으로 넘긴다.

5단계: 동결·배포

  1. 트랙 A~D가 통과하면 생산자들에게 동결을 알린다: "산출물을 동결한다. 이후 수정은 _v2 파일로 쓰고 리더에게 알려라."
  2. find deliverables game-review -type f -not -path '*/.git/*' | sort | xargs shasum > _workspace/freeze_build.sha
  3. SendMessage({to: "engineer"}, "references/deploy.md 절차로 배포하라.") → 완료 후 SendMessage({to: "qa"}, "트랙 A-4: 공개 URL 재검증").

6단계: 통합 보고서

  • Agent(name: "editor", subagent_type: "consulting-report-editor", prompt: 과제 정의 + 동결 해시 파일 경로 + 산출물 경로 목록 + 공개 URL + QA 보고서 경로)
  • 완료 → SendMessage({to: "qa"}, "트랙 E 검사") → 수정 왕복(최대 2회).
  • 보고서 작성 직전 shasum -c _workspace/freeze_build.sha 로 동결 산출물이 바뀌지 않았는지 확인한다.
