과제 3 — Meta·Google 광고 운영과 성과 분석 자동화: 적용 방안과 구현 가이드

  • 고객: 썬더게임즈(T.G Inc, 부산) · 대상 게임: 「원시인 형님들 키우기 : 문명 x 방치형 RPG」(Android 설치 500만+, 평점 4.47, iOS 병행, 인앱 결제 + 광고 수익 하이브리드)
  • 작성: 2026-10-07 · ads-growth-strategist(퍼포먼스 마케팅·마테크 관점)
  • 전제: 썬더게임즈의 실제 광고 계정·MMP·예산 데이터는 아직 받지 못했다. 이 문서의 숫자 예시와 sample/ 결과는 모두 가상 데이터다. 고객이 확인해야 할 항목은 [확인 필요]로 표시했고, 전체 목록은 _workspace/07_strategist_notes.md 에 있다.
  • API 버전·필드 이름·정책은 2026-10-07 에 공식 문서로 확인했다. 출처는 문서 끝에 있다.

한 장 요약

  • 목표: 마케팅 담당자가 매일 1시간 넘게 하던 "내려받기 → 엑셀 정리 → 국가·캠페인·소재 비교 → 보고"를 없앤다. 매일 아침 9시 전에 5줄 리포트가 메신저로 오고, 담당자는 제안된 예산 변경을 승인하거나 거절하는 데 5~15분만 쓴다.
  • 구조: 매체 API·MMP·수익 데이터를 BigQuery 에 모으고(수집), 표준 표 하나로 정리한다(정규화). 규칙 기반 분석 코드가 이상·소재 피로·예산 제안을 판정해 findings.json 을 만들고(분석), Claude 는 그 결과만 읽어 리포트 문장을 쓴다(문장화). 사람이 승인한 제안만 실행한다(승인).
  • 원칙: 숫자는 코드가 계산하고, AI 는 제안만 하며, 결정은 사람이 한다. 데이터가 의심스러우면 판단을 멈춘다. 예산 변경은 한 번에 20% 이내로, 같은 캠페인은 3일에 한 번만 바꾼다. 매체의 학습 단계를 존중하기 위해서다.
  • 로드맵: 1단계(2~3주) 노코드 커넥터 + 시트 + Claude 요약 → 2단계(4~6주) BigQuery + 분석 스크립트 + Claude API 리포트 → 3단계(8주 제안 운영 후) 승인형 예산 조정 실행.
  • 샘플로 확인한 것: 가상 데이터에 일부러 심은 문제 7건(추적 누락, 월 예산 과속, 특정 국가 CPI 급등, 소재 피로 2건, 확장 후보 소재, 예산 신호)을 분석 스크립트가 모두 잡았고, 오탐은 0건이었다. 시드 30개로 반복해도 탐지율은 90~100%였고, 오탐은 하루 평균 0.33건이었다(11장).

1. 현황 진단 — 지금의 1시간은 어디에 쓰이는가

담당자 인터뷰 전이라 아래 시간 배분은 모바일 게임 UA 실무에서 흔한 패턴을 바탕으로 한 가정이다 [확인 필요: 담당자 1일 작업 기록 1주일분].

작업 추정 시간/일 지금 하는 방식 자동화 가능 범위 사람이 해야 하는 판단
① 데이터 확인·내려받기 15분 Meta 광고 관리자, Google Ads, MMP 대시보드(있다면)에 각각 들어가 기간·국가·캠페인 필터를 걸고 내려받는다 전부 — API 로 매일 06:00 에 수집 없음
② 엑셀 정리 15분 매체마다 다른 컬럼 이름·통화·시간대를 맞추고, 설치·수익을 MMP 기준으로 바꾼다 전부 — 표준 스키마로 변환하는 SQL 매핑 규칙을 처음 한 번 정하는 일
③ 비교·이상 찾기 20분 어제·지난주와 비교해 CPI 가 튄 국가, 지친 소재를 눈으로 찾는다 대부분 — 기준선 대비 이상 탐지, 소재 피로 판정 원인 해석(시즌·경쟁작·스토어 이슈 등)
④ 예산·입찰 조정 5~10분 감으로 증감액을 정해 매체 화면에서 바꾼다 제안까지 — 규칙 기반 증감 제안 + 안전장치 승인·거절, 월 예산 배정 변경
⑤ 보고 10분 숫자를 옮겨 적어 메신저·메일로 공유한다 전부 — Claude 가 5줄 요약 작성, 숫자 검증 후 자동 발송 없음(필요하면 한 줄 코멘트)

지금 방식에는 시간 말고도 비용이 숨어 있다.

  • 늦은 발견. 추적 누락(지출은 나가는데 설치가 0)은 화면을 일일이 봐야 보인다. 며칠 늦게 알면 그동안의 예산이 측정되지 않은 채 쓰인다. 더 나쁜 경우에는 "성과가 나쁘다"고 오판해 멀쩡한 캠페인을 줄인다. 샘플 B06 이 그 예다(5·11장).
  • 판단 기준이 매일 바뀐다. 같은 CPI 상승을 어떤 날은 넘기고 어떤 날은 줄인다. 규칙을 코드로 고정하면 판단이 일관되고, 나중에 규칙 자체를 고칠 수 있다.
  • 소재 단위까지 내려가기 어렵다. 국가 6개 × 캠페인 8개 × 소재 12개를 매일 보는 것은 현실적으로 불가능하다. 그래서 소재 피로를 늦게 알아챈다.

2. 목표 상태와 원칙

목표 상태(2단계 완료 시점)

06:00 KST  수집 작업 실행(Meta·Google·MMP·수익)          — 사람 개입 없음
06:30      정규화·분석 → findings.json                   — 사람 개입 없음
06:40      Claude 가 리포트 작성 → 숫자 검증 → 메신저 발송 — 검증 실패 시 발송 보류 + 담당자 알림
09:00      담당자: 5줄 읽기 → 제안별 승인/거절 → (3단계부터) 승인분 자동 실행
수시       실시간 알림(지출 폭주, 설치 0, 수집 실패, 토큰 만료)

원칙과 이유

  1. AI 는 제안하고, 사람이 승인한다. 실행 권한이 있어도 처음 8주는 제안만 한다. 승인·거절 기록이 쌓여야 규칙을 믿고 고칠 수 있다.
  2. 데이터 정합성이 먼저다. 분석 전에 데이터 점검(신선도, 지출 대비 설치 0, 광고 수익 미적재)을 돌린다. 데이터 문제가 있는 범위는 예산 제안을 내지 않는다. 잘못된 데이터로 내린 결정이 가장 비싸다.
  3. 숫자는 코드가 계산한다. LLM 이 표를 직접 계산하면 틀린 숫자가 그럴듯하게 섞인다. Claude 는 코드가 만든 findings.json 만 읽고, 리포트의 모든 숫자는 검증기로 확인한다.
  4. 매체의 학습을 존중한다. Meta·Google 은 예산·입찰을 크게 바꾸면 학습을 다시 한다. 변경 폭 상한(20%)과 쿨다운(3일)을 규칙에 넣는다.
  5. 단계적으로 자동화한다. 노코드로 2~3주 안에 "매일 아침 리포트"를 먼저 체감하고, 그다음 코드 파이프라인과 실행 자동화로 넘어간다.
  6. 모든 판단은 근거를 남긴다. 각 제안에는 규칙, 수치, 표본 충분도(confidence), 안전장치 통과 여부가 붙는다. 누가 언제 무엇을 승인했는지도 기록한다.

3. KPI 체계 — 방치형 RPG 하이브리드 수익 기준

3.1 지표 정의

지표 계산식 왜 보는가
CPM 지출 ÷ 노출 × 1000 경매 경쟁도. 4분기(블랙 프라이데이·연말)에 오른다
CTR 클릭 ÷ 노출 소재의 첫 반응
IPM 설치 ÷ 노출 × 1000 모바일 게임 소재 평가의 핵심 지표. CTR 과 CVR 을 합친 효과다
CVR 설치 ÷ 클릭 스토어 페이지 전환. 스토어 평점·스크린샷(ASO)과 연결된다
CPI 지출 ÷ 설치 = CPM ÷ IPM 획득 단가. CPI 가 오르면 CPM(경매)·CTR(소재)·CVR(스토어) 중 무엇이 움직였는지 분해한다
Hook rate 영상 3초 조회 ÷ 노출 영상 소재의 첫 3초 흡인력(Meta)
D1·D7 잔존율 잔존 사용자 ÷ 설치 유입 품질. CPI 만 싸고 바로 떠나는 트래픽을 거른다
ROAS D0·D7 (하이브리드) (인앱 결제 수익 + 광고 수익) ÷ 지출, 설치일 코호트 누적 방치형은 광고 수익 비중이 커서 IAP 만 보면 ROAS 를 크게 낮게 본다. 샘플(가상)에서는 D0 수익의 약 50%가 광고 수익이다
ARPU D7 (IAP D7 + 광고 D7) ÷ 설치 국가 간 품질 비교
Payback 누적 ROAS 가 100%에 닿는 일수 예산 확대의 최종 기준. D7 이후는 LTV 예측 곡선으로 추정한다

3.2 하이브리드 ROAS 를 제대로 계산하기 위한 조건

  • 광고 수익을 설치 코호트에 붙여야 한다. 미디에이션(AdMob·AppLovin MAX 등)의 노출 단위 광고 수익을 사용자별로 받아 설치일·유입 캠페인에 연결한다. Firebase/GA4 의 ad_impression 이벤트를 BigQuery 로 내보내거나, MMP 의 광고 수익 연동을 쓴다 [확인 필요: 미디에이션 제품, MMP 연동 여부].
  • "광고 제거" 상품을 따로 본다. 광고 제거를 산 사용자는 광고 수익이 0이 되는 대신 IAP 가 생긴다. 이 비율이 바뀌면 ROAS 구성이 바뀌므로 주간 리포트에서 광고/IAP 비중을 함께 보여 준다(12장).
  • D7 은 7일 뒤에 확정된다. 오늘의 판단은 D0 ROAS × (과거 확정 코호트의 D7÷D0 배수)로 추정하고, 추정치임을 표시한다. 샘플에서는 직전 14일 확정 코호트의 배수(약 2.9)를 캠페인별로 계산해 쓴다.

3.3 기준값 정하는 법

  • 목표 CPI·ROAS 는 업계 평균이 아니라 자사 과거 데이터로 정한다. 국가 Tier 마다 LTV 가 크게 달라서 목표 하나로는 쓸모가 없다. 리뷰 언어 분포(ko 98 · pt 72 · en 71 · ru 41 · id 26 · es 24 · th 19)를 대리 지표로 보면 Tier 후보는 T1 KR·US(·JP), T2 BR·MX, T3 ID·TH 다 [확인 필요: 실제 집행 국가].
  • 러시아어 사용자는 따로 확인해야 한다. Google 은 2022년 3월부터 러시아에서 광고 판매를 멈췄고, Meta 는 러시아 대상 광고를 중단했다(출처 S52·S53). 2026년 현재도 유지되는지와 ru 리뷰 41건의 유입원(자연 유입, 다른 매체, CIS 국가 집행)을 MMP 로 확인한다 [확인 필요].
  • 처음 4주는 기준선을 쌓는 기간이다. 국가 Tier 별 최근 28일 중앙값을 기준선으로 삼는다.
  • 최소 표본이 있어야 판정한다. 소재는 노출 1만·설치 30건 이상, 캠페인 예산 판정은 최근 7일 지출 $200 이상이다. 표본이 부족하면 "판단 보류"로 둔다(샘플 B05).

5. 분석 로직 — 탐지 규칙, 예산 재배분, 안전장치

sample/analyze_ads.py 가 아래 규칙을 그대로 구현한다. 기준값은 모두 RULES 한곳에 모아 두었다. 초기값이므로 4주 운영 뒤 자사 데이터와 승인 기록으로 조정한다.

5.1 매일 돌리는 검사(순서대로)

# 검사 판정 규칙(초기값) 결과 유형
0 데이터 신선도·완결성 어제 날짜 행이 매체마다 있는가 / 국가×캠페인에서 지출 ≥ $30 인데 설치 0 인가(iOS 는 SKAN 지연 때문에 2일 연속일 때만) / 설치가 있는데 광고 수익이 0 인가 data_issue — 분석보다 먼저 보고
1 예산 소진 속도 매체별 (월 누적 지출 ÷ 월 예산) ÷ 경과일 비율이 ±15% 밖. 현재 일 예산 합계를 유지할 때의 월말 예상 지출과, 월 예산에 맞추려면 필요한 일 예산을 함께 계산 pacing
2 지표 이상 국가×캠페인의 CPI·CTR·D0 ROAS 가 직전 14일 기준선(중앙값·MAD) 대비 강건 z > 3, 그리고 변화 폭 ≥ 25%(CTR 20%). CPI 는 CPM·CTR·CVR 로 분해하고, 같은 국가 다른 매체가 정상인지 비교 anomaly
3 소재 피로 같은 소재의 최근 3일 CTR(구글은 IPM)이 첫 3일 대비 −25% 이상 + 메타 frequency > 3 + 차이 검정 통과 + 같은 범위의 다른 소재는 함께 떨어지지 않음 creative_fatigue
4 우수 소재 같은 캠페인에서 최근 7일 IPM 상위 20%, 중앙값의 1.3배 이상, 표본 충분, 나머지 소재 대비 차이 검정 통과 scale_creative
5 예산 재배분 5.2 규칙 budget_up / budget_down / hold

심각도 순서: data_issue > pacing(지출 이상) > anomaly(성과 급락) > creative_fatigue > scale_creative. 리포트도 이 순서로 쓴다.

매체별 차이를 규칙에 반영했다.

  • 메타는 광고(소재)×국가 단위로 판정한다. Insights API 가 level=ad 에서 country 분할을 지원하기 때문이다(S4·S5).
  • 구글 앱 캠페인은 소재가 아니라 에셋 단위 성과를 주고, 에셋 지표는 서로 겹친다. 국가 분할 가능 여부도 확인하지 못했다(4.2절). 그래서 구글 소재는 캠페인×에셋 단위로, CTR 대신 IPM 으로 판정한다. frequency 가 없으므로 메타의 "frequency > 3" 조건은 적용하지 않는다.
  • iOS 는 SKAdNetwork·AdAttributionKit 포스트백이 늦게 오므로 하루치 설치 0 만으로는 판정하지 않는다.

5.2 예산 재배분 규칙

조건 제안
대상 최근 7일 지출 ≥ $200 인 캠페인(미만이면 "판단 보류")
기준 지표 추정 D7 ROAS = 최근 7일 D0 ROAS × 직전 14일 확정 코호트의 D7÷D0 배수. 확정 D7(7~13일 전 코호트)도 함께 표시
목표 대비 ≥ 120% 이고 CPI 안정(최근 3일 CPI ≤ 직전 14일 중앙값 × 1.15) 증액 +15%(≥150%면 +20%)
최근 3일 모두 목표 대비 < 70% 감액 −20%. 확정 D7 도 70% 미만이면 "2주 지속 시 일시 중지 검토"를 덧붙인다
그 사이 유지(리포트에 쓰지 않음)

안전장치(모든 제안에 적용)

  • 변경 폭 상한 20%, 같은 캠페인 쿨다운 3일. 매체 알고리즘은 예산·입찰이 크게 바뀌면 다시 학습하고, 그동안 성과가 흔들린다. Google 은 앱 캠페인 예산·목표 CPI 를 한 번에 20% 넘게 바꾸지 말라고 권장한다(S28). Meta 는 공식 % 기준이 없어 같은 상한을 쓴다(S15, 9장).
  • 제로섬이 기본이다. 매체마다 증액분은 같은 매체의 감액분과 월 예산 여유분 안에서만 낸다. 매체 사이의 이동은 월 배정을 바꾸는 일이라 사람이 결정한다. 일 예산은 $5 단위로 맞추되, 증액은 올림·감액은 내림으로 처리해 변경 폭이 규칙보다 작아지지 않게 한다.
  • 데이터 문제가 있는 범위는 모든 제안을 보류한다. 지표 이상이 있는 범위는 증액만 막는다(원인을 확인하기 전 감액은 안전하지만 증액은 위험하다).
  • 월 예산을 과속 중인 매체는 증액하지 않는다.
  • 모든 제안에 reason(규칙 + 수치), guardrail(통과한 안전장치), confidence(표본 충분도)를 붙인다.

5.3 플레이북 초기 규칙 위에 더한 통계 안전장치 — 왜 필요한가

플레이북의 초기 규칙(z > 3, 첫 3일 대비 −25%)만 쓰면, 설치가 하루 수십 건인 범위에서는 우연한 출렁임이 이상으로 잡힌다. 같은 가상 데이터를 시드만 바꿔 30번 돌린 결과는 다음과 같다(심은 문제는 같고 잡음만 다르다).

항목 초기 규칙만 안전장치 추가 후
하루 평균 오탐 약 1.6건 0.33건(30일 10건, 그중 4건은 실제로 IPM 이 조금 높게 설정된 구글 playable 을 확장 후보로 잡은 것)
구글 소재 피로 탐지율 63% 90%
지표 이상 오탐(30일 합계) 26건 4건

셈 기준: 오탐은 심어 둔 7건에 해당하지 않는 findings 항목 수다. 시드마다 고유한 (유형·캠페인·국가·소재) 묶음을 1건으로 세고 30개 시드를 합했으며, 예산 제안은 넣지 않았다. 오른쪽 열은 python3 sample/sweep_seeds.py 30 으로 그대로 재현된다. 왼쪽 열("초기 규칙만")은 개발 중 안전장치를 넣기 전 버전으로 잰 참고값이라 지금 스크립트로는 재현되지 않는다.

더한 장치는 다섯 가지다. ① 효과 크기 하한(실무상 의미 있는 변화만 잡는다), ② z 분모에 표본 잡음 하한(1/√n), ③ 사건 수가 적으면 소재 판정 창을 3일에서 7일로 넓히기, ④ 같은 범위의 다른 소재도 함께 떨어지면 소재 피로가 아니라 범위 단위 문제로 보기(국가 CPI 급등을 소재 피로로 오판하지 않게), ⑤ 두 비율 차이 검정. 실데이터에서도 첫 4주 동안 오탐·누락을 기록해 같은 방식으로 조정한다.

5.4 진단까지 자동으로 — CPI 분해와 매체 간 비교

CPI = CPM ÷ IPM 이고 IPM = CTR × CVR × 1000 이다. CPI 가 튀면 세 요소 중 무엇이 움직였는지 계산해 조치를 고른다.

주원인 의심할 곳 자동 조치 문구
CVR 급락 + 같은 국가 다른 매체 정상 해당 매체 쪽 변화(노출 위치 구성, 최근 에셋·입찰·타깃 변경) "매체 쪽 변화 확인, 스토어 페이지 문제 가능성은 낮음"
CVR 급락 + 다른 매체도 이상 국가 공통 원인(스토어 페이지·현지화·앱 심사/배포 상태) "스토어 페이지·현지화 확인"
CPM 급등 경매 경쟁(시즌·대형 경쟁작) "입찰·타깃 점검"
CTR 급락 소재 노출 구성 "소재 피로 항목 참고"

샘플 F04 가 이 흐름을 보여 준다. 구글 T3 ID 의 CPI 가 +155% 올랐고, 분해하면 CVR −50%·CPM +25%였으며, 같은 국가의 메타 CPI 는 +12%(정상)였다. 그래서 "구글 쪽 변화 확인"을 제안했다.

6. AI(Claude)의 역할 — 계산은 코드, 해석·문장화는 Claude

6.1 분업

단계 담당 이유
수집·정규화·지표 계산 코드(SQL·Python) 결정적이어야 하고 재현할 수 있어야 한다
이상·피로·예산 판정 코드(규칙) 기준이 일관되어야 하고, 사람이 규칙을 검토하고 고칠 수 있어야 한다
우선순위 정리·리포트 문장화 Claude 여러 발견을 담당자가 읽기 쉬운 순서와 말로 엮는 일이다
원인 가설의 추가 탐색(3단계) Claude + 조회 전용 도구(MCP) "ID 는 왜 CVR 이 떨어졌지?" 같은 질문에 데이터 조회로 답한다. 판단은 사람이 한다
예산 변경 실행(3단계) 코드 — 사람의 승인 후에만 실행 권한은 별도 계정으로 분리하고 감사 로그를 남긴다

6.2 프롬프트 설계(sample/report_prompt.md)

  • 입력은 findings.json 하나다. 원본 CSV 나 대시보드 숫자는 넣지 않는다.
  • 시스템 프롬프트에 숫자 규칙을 맨 앞에 둔다. ① 입력에 있는 숫자만 쓴다, ② 퍼센트 변환과 반올림 말고는 새 계산(합계·평균)을 하지 않는다, ③ 확실하지 않으면 숫자 대신 항목 ID(F01, B02)를 쓴다.
  • 우선순위(데이터 문제 우선), 출력 형식(5줄 + 상세 표), 길이(화면 한 장)를 명시한다.
  • 원인은 findings 의 reason·action 범위 안에서만 말하게 한다. 그럴듯한 추측을 막기 위해서다.

6.3 환각 방지 — 숫자 검증기로 발송을 막는다

sample/check_report_numbers.py 는 리포트의 숫자를 모두 뽑아 findings.json 과 대조하고, 문제가 하나라도 있으면 발송하지 않고 담당자에게 알린다. 검사하는 것은 다섯 가지다.

검사 내용 막는 예
출처 findings.json 의 값(그대로·반올림·×100 퍼센트)이나 reason 문장에 이미 적힌 숫자인가 입력에 없는 합계 "$582", 지어낸 "$27,900"
단위 %가 붙은 숫자는 퍼센트 값과만, $·무단위 숫자는 퍼센트가 아닌 값과만 맞춘다 비율을 금액처럼 쓴 경우
부호 +/− 또는 "하락·상승" 같은 방향 표현이 변화량의 부호와 같은가 CTR −35% → +35%, 지출 −1% → +1%
항목 대응 줄에 F01·B01 같은 ID 나 캠페인·국가·소재 이름이 있으면, 뒤의 숫자는 그 항목의 값이어야 한다(표는 첫 칸의 ID 가 행의 주인) KR 지출에 US 값, F04 CPI 에 ID 전체 CPI, B01·B02 제안액 맞바꿈, 국가 표의 행 맞바꿈
제안 ID·캠페인 짝 제안 ID 바로 뒤의 캠페인 이름이 그 제안의 캠페인인가 "B01(META_A+APP_AOS_T1 …)"

sample/test_check_report_numbers.py 가 원본 리포트(숫자 161개, 날짜·목록 번호 제외)의 통과와 일부러 틀리게 고친 변형 13건의 차단을 확인한다. 13건에는 QA 가 쓴 바꿔치기 5건이 들어 있다. 작성 중 이전 실행값을 잘못 옮긴 숫자 1개를 검증기가 실제로 잡아내기도 했다.

검증기가 잡지 못하는 것도 있다. ① ID·이름 같은 키가 없는 문장에서 단위·부호가 같은 다른 전체 값으로 바꿔치기한 경우(예: "보류 4건"을 다른 건수로 바꿈), ② 날짜, ③ 숫자가 아닌 서술의 오류(원인 추측, 조치 문구 왜곡). 그래서 리포트 프롬프트는 키(ID·이름)를 숫자 앞에 쓰게 하고, 처음 8주는 담당자가 상세 표와 대조해 검수한다.

6.4 호출 설정(sample/make_report.py)

  • Claude Messages API(POST /v1/messages, S42), Python SDK(anthropic), 모델 claude-opus-5-5(S43), output_config.effort="low". 하루 한 번 쓰는 짧은 요약이라 낮은 effort 로 충분하다. 입력이 약 1만 토큰이므로 비용은 하루 몇 센트 수준이다(가격은 출처 S45).
  • 드물게 안전 분류기가 요청을 거절할 때를 대비해 서버 쪽 대체 실행(fallbacks="default")을 켰다. 대체 실행이 출력 도중에 일어나면 응답에 앞 모델의 잘린 글과 대체 모델의 전체 글이 함께 오므로, 마지막 fallback 블록 뒤의 글만 리포트로 쓰고 "어느 모델이 대신 썼는지"를 로그에 남긴다. 그래도 거절되면 리포트를 보내지 않고 담당자에게 알린다.
  • 하루 1회 호출이라 프롬프트 캐싱의 이득이 없어 쓰지 않는다. 결과가 메신저용 Markdown 이므로 구조화 출력(Structured outputs, S44) 대신 숫자 검증기(6.3절)로 지어낸 숫자·부호 반전·항목 바꿔치기를 막는다. 서술의 정확성은 프롬프트 규칙과 담당자 검수가 맡는다. 3단계에서 승인 버튼용 데이터를 함께 받아야 하면 구조화 출력으로 바꾼다.
  • 키·토큰은 비밀 관리자(GitHub Secrets 또는 GCP Secret Manager)에만 둔다.

학습 단계 초기화 Meta 는 마지막 중요한 수정 뒤 약 1주 안에 최적화 결과 약 50건이 쌓여야 학습을 마친다. 입찰 전략·예산 변경은 "변경 폭에 따라" 중요한 수정이 되며, 공식 % 기준은 없다(S14·S15). Google 앱 캠페인은 예산·목표 CPI 를 한 번에 20% 넘게 바꾸지 말고, 첫 전환 100건 전에는 설정을 바꾸지 말며, 예산은 목표 CPI 의 50배 이상을 권장한다(S26~S28) 변경 폭 20% 상한, 쿨다운 3일, 증액은 이벤트 시작 3일 전까지. 3단계 자동 실행도 같은 규칙을 지킨다
데이터 불일치(매체 vs MMP) 매체는 조회 기여·자체 어트리뷰션 창으로 설치를 더 많이 잡는 경향이 있고, MMP 는 매체 간 중복을 한 곳에 귀속한다 판정은 MMP 기준으로 통일한다. 매체÷MMP 설치 비율을 주간 리포트로 보고, 비율이 급변하면 data_issue 로 올린다
수익 데이터 누락 광고 수익(미디에이션)이 하루 이틀 늦게 오거나 연동이 끊기면 하이브리드 ROAS 가 크게 낮게 나온다 검사 0의 "설치가 있는데 광고 수익 0" 규칙. D0 판단을 보류하고 다음 날 재계산한다
러시아 등 집행 불가 지역 Google·Meta 는 2022년부터 러시아 내 광고를 중단했다(출처 S52·S53) ru 사용자 유입원을 MMP 로 확인한다. ru 는 접속 장애 해결 전까지 집행·프로모션을 보류한다(12장) [확인 필요]
개인정보 MMP 원시 데이터·사용자 단위 수익에는 기기 식별자가 들어간다. 한국 개인정보 보호법, 각국 규정이 적용된다. iOS 는 다른 회사 앱·웹을 넘나드는 추적이나 광고 식별자 접근에 앱 추적 투명성(ATT) 동의가 필요하다(S54) [확인 필요: 국내 법무 검토 범위] 집계 지표만 적재한다. 사용자 단위 데이터가 꼭 필요하면 BigQuery 안에서만 집계하고, 접근 권한·보존 기간을 정한다. 광고 계정 데이터를 외부 LLM 에 보낼 때는 집계 결과(findings.json)만 보낸다
LLM 오류 숫자를 지어내거나, 부호·항목을 바꾸거나, 원인을 과하게 추측할 수 있다 입력 제한(findings.json 만), 숫자 검증기(출처·단위·부호·항목 대응)로 발송 차단, 원인은 reason·action 범위 안에서만 쓰게 하고 처음 8주는 사람이 검수한다(6장). 검증기는 키 없는 문장의 같은 단위 바꿔치기와 서술 오류를 잡지 못한다
자동화 과신 규칙이 놓치는 상황(신작 경쟁작 출시, 스토어 피처링, 서버 장애)이 있다 처음 8주는 제안만 한다. 주간 리포트에 "규칙 성과" 절을 두고, 담당자가 거절한 이유를 규칙에 반영한다

  1. 4장의 수집 스크립트로 raw_* 표를 채우고 transform.sql 로 3.4절 표준 컬럼의 ads_daily 를 만든다.
  2. ads_daily 를 CSV 로 내보내거나, analyze_ads.load_rows() 를 BigQuery 조회로 바꾼다. 스키마는 그대로 둔다.
  3. budget_config.json 을 실제 월 예산·일 예산·변경 이력(매체 API 의 변경 이력 또는 approvals 표)·목표 ROAS 로 채운다. is_sample_data 를 false 로 바꾸면 리포트 머리말에서 "가상 데이터"가 빠진다.
  4. 처음 4주는 결과를 발송하되 제안은 참고용으로만 쓰고, RULES 를 조정한다.

12. 과제 1·2 와의 연결

세 과제는 따로 굴러가지 않는다. 리뷰(과제 1)는 광고 수익 구조와 스토어 전환율에 영향을 주고, 주간 이벤트(과제 2)는 UA 소재와 집행 타이밍을 정한다.

12.1 과제 1(리뷰 대응) ↔ 광고 수익·스토어 전환

  • 광고 피로가 리뷰에 이미 보인다. 최근 60일 리뷰 378건 가운데 광고 관련 리뷰가 20건(광고 불만 14건, 광고 시청 뒤 재시작·X 버튼 먹통 같은 버그 5건, 광고 보상 미지급 1건)이고, 1~2점 리뷰 57건 중 15건이 광고 관련이다(과제 2 이벤트 캘린더 1장, analyst 분류 기준). "광고 제거와 자동 사냥을 따로 파는 건 아쉽다"는 리뷰도 있다.
  • 광고 빈도를 줄이면 ROAS 가 바뀐다. 방치형은 광고 수익이 ROAS 의 큰 몫이다(샘플 가상값으로는 D0 수익의 약 50%). 운영팀이 리뷰 대응으로 광고 빈도를 낮추거나 광고 제거 상품을 바꾸면, 광고 수익 ARPU 가 내려가고 IAP 가 오를 수 있다. 이 변화를 반영하지 않으면 UA 목표 ROAS 가 틀린 기준이 된다. → 광고 정책을 바꾼 날을 budget_config 의 이벤트 로그에 남기고, 주간 리포트의 광고/IAP 비중 추이(7.2절)로 영향을 따로 본다.
  • 평점은 CVR 이다. 스토어 평점(현재 4.47)과 최근 리뷰는 스토어 페이지 전환율(CVR)에 영향을 준다. 광고 관련 1~2점 리뷰가 늘면 CVR 이 떨어지고 CPI 가 오른다. → 주간 리포트에 국가별 CVR 과 해당 언어 리뷰의 광고 불만 비율을 나란히 둔다. 과제 1 대시보드의 분류 결과(category=ads, bug)를 BigQuery 로 함께 적재하면 바로 붙일 수 있다.
  • 광고 시청 관련 버그는 수익 데이터 이상으로도 나타난다. "광고를 본 뒤 재시작·빈 화면" 같은 버그는 광고 수익 급감 또는 광고 노출 수 급감으로 먼저 보일 수 있다. 데이터 점검(검사 0)의 광고 수익 미적재 규칙이 이런 신호를 함께 잡는다. 과제 1의 bug 분류와 날짜를 맞춰 보면 원인을 빨리 찾는다.
  • UA 소재에서 "광고 없음"을 약속하지 않는다. 제품을 오해하게 만드는 광고는 Google 의 허위 진술(Misrepresentation) 정책과 Meta 광고 표준의 기만적 관행 금지에 걸릴 수 있고(S55·S56), 설치 뒤에는 실망 리뷰로 돌아온다. 소재 문구는 실제 게임 시스템(보스토벌·장비 합성·형님의 탑·토템 등)에 맞춘다.

12.2 과제 2(주간 이벤트) ↔ UA 소재·집행 타이밍

  • 이벤트 키아트를 UA 소재로 재사용한다. 과제 2는 이벤트마다 글자 없는 키아트 3규격(16:9 · 9:16 · 1:1)을 만든다. 이것을 메타 피드·스토리·릴스와 구글 앱 캠페인 이미지 에셋으로 바로 쓰면 소재 교체 주기를 맞출 수 있다. 소재 피로 탐지(F05·F06)가 "교체 소재 필요"를 알리면, 다음 이벤트 키아트로 교체 소재를 만든다.
  • 이벤트 일정에 맞춰 UA 를 미리 준비한다. 이벤트 시작 3~5일 전에 이벤트 테마 소재를 테스트 캠페인에 넣어 학습을 끝내 두고, 이벤트 기간에는 검증된 소재 위주로 집행한다. 이 기간에는 예산 쿨다운 규칙이 겹치므로, 증액은 이벤트 시작 3일 전까지 끝낸다.
  • W44 할로윈(10/26~11/01): 키아트가 이번 주 완성되므로 10/21~23 에 소재 테스트를 시작할 수 있다.
  • W48 블랙 프라이데이(11/23~29): 미국을 중심으로 CPM 이 오르는 기간이다. 이벤트가 "광고 제거·자동 사냥 묶음 혜택"이라 IAP 전환이 오르고 광고 수익 비중은 내려갈 수 있다. 이 주의 ROAS 기준값은 따로 보고, 신규 획득보다 복귀 사용자 대상(리타기팅·앱 참여 캠페인) 비중을 검토한다 [확인 필요: 복귀 사용자 캠페인 운영 여부].
  • 러시아어권은 이벤트도 UA 도 장애 해결이 먼저다. 과제 2 캘린더는 ru 접속 장애 리뷰 14건 때문에 ru 스토어 프로모션 노출을 장애 해결 뒤로 미뤘다. UA 쪽도 같은 원칙을 쓴다. 게다가 Meta·Google 로는 러시아 내 집행이 어렵다(3.3절).
  • 이벤트 기간 성과를 분리해 본다. 이벤트 기간에는 잔존·결제가 평소와 달라 D7 배수가 흔들린다. 분석 코드에 이벤트 캘린더를 입력으로 넣어 "이벤트 기간" 표시를 붙이고, 기준선(14일 중앙값)에서 이벤트 기간을 따로 다룬다(2단계 과제).
