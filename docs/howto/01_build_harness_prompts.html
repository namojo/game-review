## 과제별 요구
1. 과제 1: 실제 공개 리뷰(최근 60일, 두 스토어, 전 언어)를 수집해 유형·우선순위(P1~P3)·담당 부서로 분류하고, 한국어 번역과 GM Mr. Bow 말투의 답변 초안을 만든다. 담당자가 검수·승인하는 웹서비스(정적 SPA)를 만들어 https://namojo.github.io/game-review/ 에 배포한다(저장소 namojo/game-review, GitHub Pages). 리뷰가 많으므로 언어별 배치로 나눠 분석 에이전트를 병렬로 돌린다. 실제 스토어에 답변을 등록하지는 않는다. 등록 스크립트는 기본 dry-run으로 만든다.
2. 과제 2: 향후 8주 이벤트 캘린더와 이번 주 이벤트 키트 1개(기획서, 다국어 copy.json, 스토어 등록 시트)를 만든다. 이미지는 codex-image 스킬(codex exec image_generation)로 글자 없는 키아트 3규격(16:9·9:16·1:1)을 병렬 생성하고, 언어별 문구는 스크립트로 합성한다. 게임 스크린샷을 화풍 참고로 쓴다. 리뷰 분석 결과(불만 유형)를 이벤트 설계에 연결한다.
3. 과제 3: IT마케팅(퍼포먼스 마케팅·마테크) 전문가 관점으로 구현 가이드를 쓰고, 가상 데이터로 실제 동작하는 분석·일일 리포트 샘플을 만든다. 숫자는 코드가 계산하고 Claude는 문장만 쓰게 한다. API 버전·정책은 공식 문서로 확인하고 출처를 단다.

과제 1만 — 리뷰 대응

/harness:harness

「{게임명}」(Google Play {패키지명}, App Store {앱 ID})의 스토어 리뷰 대응 하네스를 만들어줘.

- 현재: 운영 담당자가 리뷰를 직접 읽고 번역해 미리 써 둔 답변을 고른다. 1건 2분. 바쁘면 며칠 치를 몰아서 처리한다.
- 목표 흐름: 리뷰 수집 → 유형 분류(P1 돈·계정·진행 불가 / P2 / P3) → 한국어 번역 → 답변 초안(GM {서명} 말투, 리뷰 언어로) → 담당자 검수 → 답변 등록
- 구성: 수집·배치 스크립트, 언어 배치별 분석 에이전트(병렬), 검증 스크립트(Play 350자, 답변 언어, 금지 표현), 검수 웹서비스(정적 SPA, GitHub Pages {URL}), 승인 답변 등록 스크립트(기본 dry-run, 공식 API), QA 에이전트
- 제약: 사람이 승인하기 전에는 등록하지 않는다. 답변에서 날짜·보상을 약속하지 않고 개인정보를 묻지 않는다. 작성자 이름은 해시로 바꾼다. 매일 실행해도 기존 리뷰와 분석이 사라지지 않게 누적 병합한다.
- 산출물: game-review/(웹서비스+pipeline/), deliverables/task1-review-automation/guide.md
- 재실행 요청 "리뷰 데이터 갱신"이 동작하게 해줘.

/harness:harness

「{게임명}」 게임 내 주간 이벤트 제작 하네스를 만들어줘.

- 에이전트: 라이브옵스 기획자, 비주얼 디자이너, QA
- 제약: 없는 게임 시스템·보상 수치를 지어내지 않고 [기획 확인 필요]로 표시한다. 스토어 이미지에는 글자를 넣지 않는다. 문구의 단일 원천은 copy.json. 글자 수 한도를 검증한다. 국가별 추모일·종교·광고 법규를 확인한다.
- 산출물: deliverables/task2-weekly-event/event_calendar.md, {event_id}/ 아래 event_brief.md · copy.json · store_submission.md · keyart/ · localized/

과제 3만 — 광고 운영·분석

/harness:harness

「{게임명}」 Meta·Google 광고(UA) 운영·성과 분석 자동화 하네스를 만들어줘. 퍼포먼스 마케팅·마테크 전문가 관점이다.

- 현재: 마케팅 담당자가 매일 1시간 넘게 매체 화면을 확인하고 엑셀로 비교한다.
- 목표 흐름: 데이터 수집(Meta Marketing API, Google Ads API, MMP) → 성과 분석 → 문제점 파악(추적 누락, CPI 급등, 소재 피로, 예산 과속) → 예산·다음 액션 제안(변경 폭 상한, 쿨다운) → 5줄 일일 리포트
- 산출물: deliverables/task3-ads-automation/guide.md(KPI, 데이터 아키텍처, 탐지 규칙, Claude 역할, 리포트 설계, 로드맵, 리스크, 출처), sample/(가상 데이터 생성기, 분석 스크립트, findings.json, 리포트 프롬프트, 숫자 검증기, 샘플 리포트)
- 제약: 숫자는 코드가 계산하고 Claude는 findings.json만 읽어 문장을 쓴다. 리포트 숫자는 검증기로 확인한다. 실제 데이터가 없으면 가상 데이터임을 모든 파일에 표시한다. API 버전·정책은 공식 문서로 확인하고 출처를 단다. 확인하지 못한 것은 [확인 필요]로 둔다.
- 재실행 요청 "과제 3만 다시", "어제 데이터로 일일 리포트"가 동작하게 해줘.

(c) 좋은 프롬프트의 요소

요소 왜 필요한가 이 프로젝트의 예
과제 정의 에이전트 역할과 범위가 여기서 정해진다 과제 3개, 담당 부서
현재 방식·소요 시간 ROI 계산과 "무엇을 자동화할지"의 기준이 된다 리뷰 1건 2분, 디자인 1~2일
검토 방향(단계명) 고객 용어 그대로 흐름도·스킬 단계가 만들어진다 수집 → 분류 → 번역 → 초안 → 검수 → 등록
산출물 형식·위치 나중에 재실행·검수할 때 같은 곳에 쌓인다 deliverables/task2-weekly-event/{event_id}/
도구 하네스가 쓸 수 있는 도구를 미리 알아야 설계가 맞는다 codex-image, gh, venv
제약 자동화가 넘으면 안 되는 선 사람 승인 전 등록 금지, 수치를 지어내지 않음, 이미지 글자 금지
재실행 시나리오 오케스트레이터가 부분 실행을 지원하게 된다 "다음 주 이벤트 키트"

나쁜 예

우리 게임 리뷰 자동으로 답변하는 거 만들어줘.

이렇게 쓰면 어떤 스토어인지, 누가 검수하는지, 어디에 배포하는지, 어떤 답변이 금지인지가 빠진다. 하네스가 가정을 채우게 되고, 결과가 회사 운영 방식과 맞지 않는다.

좋은 예 — 같은 요청을 다듬은 것

/harness:harness
「원시인 형님들 키우기」 Google Play·App Store 리뷰 대응 하네스를 만들어줘.
현재 운영 담당자가 리뷰를 직접 번역해 미리 쓴 답변 4~5종을 돌려 쓰고(1건 2분), 바쁘면 며칠 치를 몰아서 처리한다.
흐름은 리뷰 수집 → 유형 분류(P1~P3, 담당 부서) → 한국어 번역 → GM Mr. Bow 말투 답변 초안 → 담당자 검수 → 답변 등록.
검수 웹서비스는 GitHub Pages(namojo/game-review)에 배포하고, 등록 스크립트는 기본 dry-run.
사람 승인 전 등록 금지, 날짜·보상 약속 금지, 개인정보 요구 금지. 매일 실행해도 누적되게.

(d) 하네스가 만들어지면 확인할 것

ls .claude/agents .claude/skills
sed -n 1,40p CLAUDE.md
확인 기준
에이전트 과제마다 생산자 1명 이상 + QA 1명. 각 정의에 "핵심 역할·작업 원칙·입력·출력 규칙·통신 규칙·오류 처리"가 있다
스킬 각 SKILL.md 에 산출물 경로, 단계별 명령, 재실행 방법이 있다. 결정적 작업(수집·합성·검증)은 scripts/ 에 스크립트로 있다
오케스트레이터 "0단계 기존 작업 확인"(처음/부분/새 실행 판단), 단계별 병렬 실행, QA 왕복 상한, 오류 처리 표가 있다
CLAUDE.md 호출 조건(어떤 말에 하네스가 동작하는지)과 변경 이력 표가 있다
첫 실행 하네스를 만든 같은 세션에서는 새 에이전트 유형이 아직 등록되지 않아 Agent type not found 가 날 수 있다(2026-10-07 실제로 겪음). Claude Code를 다시 시작하거나, 오케스트레이터에 "이름을 붙여 호출하고 프롬프트 첫 줄에 역할 정의 파일을 읽게 한다"는 대응이 들어 있는지 본다

하네스 개선 요청 — /harness:evolve

실행해 보고 아쉬운 점이 있으면, 그 경험을 하네스에 반영하게 한다. 개선 내용은 에이전트·스킬·오케스트레이터와 CLAUDE.md 변경 이력에 남는다.

/harness:evolve

이번 실행 회고를 하네스에 반영해줘.
1. 키아트 재생성이 반복돼 너무 오래 걸렸다 → 재생성은 1회까지만 하고 남은 문제는 "알려진 제한"으로 기록하게 해줘.
2. codex 전역 기본 모델이 ChatGPT 로그인에서 지원되지 않아 실패했는데 스크립트가 [ok] 로 오판했다 → 새로 만든 파일만 성공으로 보고, CODEX_MODEL 로 모델을 지정할 수 있게 해줘.
3. Google Play 프로모션 이미지도 글자가 금지인데 스킬 문서는 합성 배너를 Play용이라고 적었다 → store-event-specs.md 와 SKILL.md 를 고쳐줘.
4. 스토어 제출 시트가 규격 미달 원본을 가리켰다 → 제출 이미지는 keyart/store/ 규격 사본을 쓰도록 절차와 시트 양식을 고쳐줘.

위 네 항목은 이 프로젝트에서 실제로 겪고 고친 것이다(_workspace/progress.md "하네스 개선 기록").
